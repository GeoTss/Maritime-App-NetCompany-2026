# UI Round (the six redesign boards) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the six redesign boards of the 2026-11-17 UI review into the ops console, in six waves, and move the console to the user's chosen visual world, Signal hoist (dark, screen tabs only). The first wave is the answer drawn on the map, the purchase-order decision and a confirm that restates the order. The second wave is the new world.

**Architecture:**
- The map and the approvals screen read stored calculations by id through two new GET endpoints, so an answer's map view is the exact calculation it cited.
- The approval view gains the whole bunker plan, built by the existing shared fact builder in `apps/api/src/facts/bunker.ts`. That includes one new derived fact, the margin over the runner-up, computed by `packages/domain`'s `calculate`.
- Everything else is web-only: tokens, copy, layout. Tool output, prompts and fact ids stay byte-identical. The one exception is planned and contained: the demo story's calculation numbering shifts by one (ruling U1).

**Tech Stack:** TypeScript 6 ESM, Zod (`packages/shared`), Hono (`apps/api`), React 19 + Vite + Tailwind 4 + shadcn radix-mira + MapLibre (`apps/web`), Vitest + Testing Library, Playwright (`e2e/demo.spec.ts`).

**Spec:** `docs/UI_REVIEW.md` holds the critique, the user's decisions, the board index and the Signal hoist world.
- **Layout, content and behaviour:** the boards in `docs/design/ui-round/*.dc.html`, plain HTML with inline styles. Their look is the old world.
- **The look:** the Signal hoist sketches in `docs/design/signal-hoist/{map,inbox,approvals,evaluation}.html`, and the direction contract in `apps/web/.impeccable/surfaces/src-app-tsx.md`.

Read the board and the sketch a task names before building it. Their numbers are the recorded demo's.

## Global Constraints

- **Maths and facts.** All maths is deterministic code in `packages/domain`; the UI computes no business number and never animates a cited fact. Every number shown to a user comes from a tool or view fact and is cited (CLAUDE.md rules 1–2).
- **No byte drift.** Never change a prompt, a tool's input or output, a fact id or label a tool returns, or the bytes of any model request. Free dev replays must stay scorecard-identical (`scripts/check-scorecard.sh`) at every gate. The one sanctioned change is ruling U1's story re-record.
- **UI rules** (CLAUDE.md, verbatim):
  - "Never build toasts, drawers, command menus, dialogs, dropdowns or number tickers from scratch: use sonner, vaul, cmdk, shadcn `dialog` / `dropdown-menu`, and `@number-flow/react` (through `MetricNumber`)."
  - "Components are installed with the shadcn CLI (`npx shadcn@latest add …`; the lead only, with the repo-local npm cache)."
  - "Map every UI need to its library with the `pick-ui-library` skill before writing feature code."
  - "At most one animated focal component per page (Magic UI `ripple` on the map, `border-beam` on approvals)."
  - "Colours, radius, type and fonts come from the tokens in `apps/web/src/styles/globals.css`; no raw hex in components; fonts are bundled (no CDN)."
  - "The UI computes no business number and never animates a cited fact; untrusted text (AIS, hazards, email) renders as text only."
  - "Run `npx impeccable detect` and look at the screen in the browser pane before calling UI work done."
- **The visual contract** is the Signal hoist world (`docs/UI_REVIEW.md`, "The Signal hoist world"), applied in Task 9:
  - each hue has one job, and there is no green;
  - the one solid primary is true signal blue;

- **Tokens before Task 9.** Wave 1 builds on the existing semantic tokens (`beacon`, `go`, `caution`, `alarm`, `lamp`); Task 9 remaps them. Never hard-code a world colour in a component.
- **DESIGN.md.** Task 9 updates its frontmatter tokens and fonts so the design hook checks the new world. The impeccable documenter rewrites the whole file from the built world in Task 17.
- **Secrets.** Never read, print or log `.env`. Never run `docker compose config` in the working copy.

## Rulings

- **U1. Show stored calculations, never re-plan to display an answer.**
  - **Decision:** "Show on map" draws the calculation the answer cited, through `GET /api/route-plans/:id` and `GET /api/bunker-plans/:id`.
  - **Cost:** the story no longer POSTs a plan for Aegean Pioneer after the route question. The later instruct turn's plan becomes calculation 4 instead of 5, so its recorded replies miss. Record mode is replay-first, so only that turn is re-recorded, for an estimated few cents of Claude Haiku 5.5 calls. Task 8 asks the user for the budget.
  - **Fallback if no budget:** the story clicks "Plan route again" once after the stored plan appears, which keeps the numbering, and nothing is re-recorded.
- **U2. The runner-up margin is a derived fact the tool never returns.**
  - **Id and value:** id `f_plan_bunkering_<calcId>_marginVsRunnerUpUsd`. Value from `calculate("subtract", [runnerUpTotal, bestTotal])` in `@pharos/domain`.
  - **Provenance:** `{ source: "derived", operation: "subtract", operands: [runnerUpTotalId, bestTotalId] }`.
  - **Label and scope:** label `<scope>Margin of the best option over the runner-up, in total cost`. The runner-up is the first feasible option after the best in rank order. No runner-up, or no best option, means `null`.
- **U3. The answer's plan is the cited calculation with the highest id.** It is taken from `response.facts` whose provenance is `calculation` with calculator `planBunkers` (a bunker plan) or `route_speed` (a route plan).
- **U4. Auto-draw happens only on the map.** When an answer arrives while the location is `/`, the dock navigates (replace) to the answer's map link. Elsewhere, the answer shows a "Show on map" link.
- **U5. Route plans for public ships are not served by id.** `GET /api/route-plans/:id` returns 404 when the stored plan's subject is an AIS ship (`mmsi` not null), and the answer link then selects the ship only. Fleet-vessel plans are served with facts byte-identical to the `POST /api/route-plan` response for the same calculation.
- **U6. Approvals selection lives in `?recommendation=<id>`.** This is the existing deep-link parameter.
  - **Default:** the first awaiting proposal, else the newest decided one.
  - **Order:** awaiting proposals oldest first (the order they were proposed), decided ones newest first.
- **U7. One meaning per colour, in the Signal hoist world.**
  - **Yellow** means "needs you": needs review, awaiting a decision, a vessel alert.
  - **Light signal blue** means act, recommended, and a positive saving.
  - **Red** means blocked, hazard or reject.
  - **Recorded mode** is neutral: a hollow text-2 dot and the mode word in text-1. "model: recorded" is a neutral tag. "Live" is the mode word in text-1 with a filled text-1 dot.
  - **"Extracted", "executed" and "accepted after fix"** are neutral with a check icon; the last reads "corrected". Approved and rejected carry the C and N flags.
  - **No green** anywhere: the `go` token is retired.
- **U8. Atkinson Hyperlegible Next for everything, times included, with tabular figures.** Atkinson Hyperlegible Mono is for identifiers only: IMO, MMSI, UN/LOCODE, voyage numbers, email addresses, fact ids, model ids and prompt versions. Coordinates use Next. Archivo and B612 Mono leave the bundle.
- **U9. Plain-text email bodies render in Atkinson Hyperlegible Mono** (`--font-verbatim`), so a sender's column alignment survives.
- **U15. The world is Signal hoist, dark.** It replaces the night-watch desk; it is not a skin over it. The ICS state flags are a component (`StateFlag`, kinds K, V, U, C, N), always rendered beside a word and never alone. Assistive technology reads the word, so the flag is `aria-hidden`.
- **U16. Navigation is four screen tabs in a 48 px top bar.** The 44 px nav rail and the 36 px status strip merge into it, and there are no subject tabs (the user's words: "without the extra tabs"). The design kit leaves the operator's navigation for a Developer group in ⌘K.
- **U10. "Needs you" is assembled in the web from existing GETs:** vessel alerts, emails in `needs_review`, pending proposals and active hazards. Its count is a count of items, not a business number. There is no new endpoint.
- **U11. Check wording is mapped in the web** (`CHECK_COPY`), 1-based. The API's stored check names and details are unchanged, which keeps stored data and the golden sets untouched.
- **U12. The model's answer text is never rewritten.** The UI adds structure around it: real lists for Markdown bullets, and tables built from the cited calculation's facts.
- **U13. Quantity alternatives ("300/350 mt") come from a domain normaliser** served with the review item. The UI never parses numbers out of email text.
- **U14. Out of scope:**
  - the "/ mt" unit normaliser, the multi-turn caveat and the grader limits (all measured work, in architecture wave 3);
  - the all-vessel bunker label prefix (A8);
  - native date inputs in the review form (a calendar component is a dependency change, so it is parked);
  - live-mode-only behaviour.

## Review Focus

1. **A stored plan id that is missing or of the wrong kind** (`/?bunkerPlan=999`, `/?routePlan=<a bunker calc id>`). The map should say "Plan 999 could not be found", keep every other layer working and offer Clear. Tested in Task 3 (404 for the wrong kind) and Task 4 (the message).
2. **A bunker plan with one feasible option, or whose best option is missing.** There should be no margin and no runner-up line; the chart and the map draw what exists. Tested in Task 2 and Task 6.
3. **An answer that cites no plan** (a fleet list, a vessel status). There should be no map link and no navigation. Tested in Task 5.
4. **Approvals with nothing pending, or a deep link to an unknown id.** The detail should show the newest decided proposal, or "Proposal 42 is not in the list" beside the queue. Tested in Task 6.
5. **A 375 px screen.** The approvals queue stacks above the detail, the map chip and legend clear the panel, and nothing scrolls sideways. Checked in each wave gate with `resize_window` at 375 px.

```ts
export const BUNKER_MARGIN_PATH = "marginVsRunnerUpUsd";
export function bunkerPlanView(
  c: BunkerFactContext,
  meta: {
    grade: FuelGrade;
    vesselId: Id | null;
    voyageNo: string | null;
    /** The option's port, or null when unknown (the option is then left out of the view). */
    port: (optionId: string) => BunkerOptionView["port"] | null;
  },
): BunkerPlanView;
```

- **Rows.** Each option's `rows` are built in this order and with these names, by the existing `optionFacts` helper so ids and labels equal the tool's:
  1. `qtyMt` "quantity";
  2. `headlinePriceUsdPerMt` "headline price";
  3. `totalCostUsd` "total delivered cost";
  4. `effectivePriceUsdPerMt` "effective price (total cost per mt)";
  5. `delayHours` "delay";
  6. `etsCostUsd` "EU ETS cost";
  7. `fuelEuCostUsd` "FuelEU exposure".
- **Shortcut fields.** `headlinePrice`, `totalCost` and `delay` are the same Fact objects as in `rows`.
- **Margin.** Ruling U2.
